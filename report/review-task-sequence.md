## 4. Обязательный чеклист

### 4.1 Нотация UML sequence (по методичке)

- Есть ли корректные линии жизни участников и временной порядок сверху вниз.
- Сообщения имеют понятные, сценарные имена действий, а не случайный API-жаргон.
- и тд

### 4.2 Трассировка к сценариям

- Шаги сценария 1 («Ввести название лабиринта») покрыты 1:1.
- Альтернатива A1 (отмена) отражена во всех точках, где она разрешена сценарием.
- Альтернатива A2 (пустое название) отражает правильный возврат к нужному шагу сценария.
- Шаги сценария 2 («Изменить тему оформления») покрыты 1:1.
- Предусловия НЕ подменены шагами основного потока.

### 4.3 Согласованность с другими UML-артефактами

- Названия ВИ и переходы согласованы с `use-case.puml`.
- Поведение по «Выйти из уровня»/сбросу темы не противоречит `player.puml`.
- Никаких логических конфликтов между sequence/state/use-case.

### 4.4 Качество для защиты

- Подписи читаемые и в одном стиле.
- Нет мелких визуальных/смысловых дефектов, за которые могут «снять балл».
- Формулировки в `2.4.6-sequence-diagram.md` полностью соответствуют диаграммам.
- В тексте нет утверждений, которых нет на диаграммах (и наоборот).

## 5. Что считать ошибками по severity

### Bugs (критично)

- Неверная логика потока/альтернатив.
- Нарушение требований методички.
- Несоответствие шагам сценария.
- Противоречие с use-case/state.

### Warnings (средне)

- Спорные нотационные решения.
- Избыточные/неудачные сообщения, ухудшающие защиту.
- Недостаточно аккуратная трассировка в тексте 2.4.6.

### Suggestions (низко)

- Улучшения читаемости и формулировок.

---

## 6. Формат ответа ревьюера

Ответ обязательно в формате:

1. `Bugs` — список по убыванию серьёзности, с привязкой к файлу и строке.
2. `Warnings` — список с файлами/строками.
3. `Suggestions` — список улучшений.
4. `Итог` — короткий вердикт: «готово к защите / не готово», и почему.

Для каждого пункта указывай:

- где проблема (`path:line`),
- почему это ошибка (ссылка на источник из п.2),
- как исправить (конкретная правка).
