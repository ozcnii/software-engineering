## Analysis

План относится только к будущей секции `3.2.2 Диаграмма развертывания` и не является итоговым текстом секции для переноса в `report/ours.docx`.

В качестве учебной основы используются лекции:

- `refs/7  Диаграмма развертывания 2025.pptx` — основной источник по нотации диаграммы развертывания;
- `refs/6  Диаграмма компонентов 2025.pptx` — вспомогательный источник по компонентам, зависимостям и стереотипам файловых артефактов;
- `refs/8  Диаграмма классов 2025.pptx` — источник для ограничения области: отношения классов, атрибуты, операции, агрегации, композиции и физическая модель БД не должны переноситься в диаграмму развертывания.

По лекции 7 диаграмма развертывания показывает общую конфигурацию и топологию распределенной программной системы, узлы выполнения программных компонентов, размещение компонентов по узлам и физические соединения между аппаратными устройствами. Узел является физически существующим элементом системы и может иметь стереотип `<<processor>>`, а сеть может быть показана как узел со стереотипом `<<net>>`. Соединения между узлами являются разновидностью ассоциации и изображаются линиями без стрелок.

По лекции 6 для физических программных элементов допустимы стереотипы `<<file>>`, `<<executable>>`, `<<library>>`, `<<script>>`, `<<source>>`, `<<document>>`, `<<table>>`. Эти стереотипы нужно применять к артефактам аккуратно: программы и сервисы на диаграмме в стиле эталона лучше показывать как компоненты внутри физических узлов, а файловые стереотипы использовать только для файлов, исходников, скриптов и библиотек. Браузерный frontend не является самостоятельным физическим процессором и не должен обозначаться как отдельный узел; JavaScript/frontend-артефакты ближе к `<<script>>` или `<<source>>`, а не к `<<executable>>`.

В качестве эталона оформления используется `refs/reference-6413-puzzles.pdf`. В эталоне раздел `3.2.2 Диаграмма развертывания` оформлен кратко: теоретическое описание, один рисунок и текстовое описание узлов, файлов, приложения и соединения с сервером базы данных. Сама диаграмма эталона выполнена в стиле распределенной топологии: `Клиент <<processor>>`, `Сервер <<processor>>`, промежуточная сеть `<<net>>`, компоненты/файлы внутри физических узлов и физические соединения между узлами.

Фактическая среда приложения подтверждается материалами проекта: приложение является веб-приложением `Лабиринт`, frontend работает на React/Vite, backend работает на NestJS, база данных PostgreSQL запускается в Docker-контейнере через Docker Compose, взаимодействие frontend/backend выполняется по REST JSON, backend подключается к PostgreSQL через Prisma.

## Open questions

На момент утверждения плана приняты следующие решения:

1. Диаграмма должна быть выполнена в стиле эталона, то есть как логическая распределенная UML-топология с физическими узлами клиента, сервера приложения, сервера базы данных и сетью между ними.
2. Диаграмма не должна оставаться one-node схемой с одной `Рабочей станцией локального запуска`, потому что это хуже соответствует эталону и лекционному акценту на топологию распределенной системы.
3. Физические узлы верхнего уровня:
   - `Клиент <<processor>>`;
   - `Сервер приложения <<processor>>`;
   - `Сервер базы данных <<processor>>`;
   - `Сеть <<net>>`.
4. Внутри `Клиент <<processor>>` нужно показать:
   - `Операционная система`;
   - `Браузер`;
   - `React frontend <<script>>` как клиентский код, выполняемый браузером.
5. Внутри `Сервер приложения <<processor>>` нужно показать:
   - `Операционная система`;
   - `Node.js runtime`;
   - `Vite dev server`;
   - `NestJS backend API`;
   - `Prisma Client <<library>>`;
   - `app/frontend <<source>>`;
   - `app/backend <<source>>`.
6. Внутри `Сервер базы данных <<processor>>` нужно показать:
   - `Операционная система`;
   - `Docker Engine`;
   - `docker-compose.yml <<file>>`;
   - `Контейнер labyrinth-postgres`;
   - `PostgreSQL 16`;
   - `Файлы данных PostgreSQL <<file>>`.
7. Docker показывается только для PostgreSQL: `app/docker-compose.yml` подтверждает контейнер `labyrinth-postgres`, но не подтверждает контейнеры frontend/backend.
8. Docker Compose не показывается как среда выполнения или физический узел. `docker-compose.yml` показывается как файл-артефакт `<<file>>`, который описывает запуск контейнера PostgreSQL.
9. Между физическими узлами и сетью используются только линии без стрелок, как в лекции и эталоне. На этих линиях можно подписывать протоколы и порты.
10. Зависимости между артефактами и библиотеками не нужно смешивать с физическими соединениями. Если они нужны на диаграмме, их нужно показывать пунктирной зависимостью или вложением, но не той же линией, что физический канал между узлами.
11. `localhost` нельзя использовать в подписях межузловых соединений. Для диаграммы в стиле эталона нужно указывать только протоколы и порты: `HTTP 5173`, `HTTP / REST JSON 3001 /api`, `PostgreSQL 5432`.
12. Подписи протоколов на линиях через `Сеть <<net>>` обозначают маршруты обмена данными между узлами, а не зависимости между внутренними компонентами.
13. Открытым остается только технический вопрос нумерации рисунка `N`, потому что итоговая нумерация зависит от ручного переноса в `report/ours.docx`.

## Data flow / API / state mapping

Будущая диаграмма развертывания должна отразить следующие связи в форме логической клиент-серверной топологии:

1. Пользователь работает с приложением через браузер на узле `Клиент <<processor>>`.
2. Клиентский браузер получает frontend-код с узла `Сервер приложения <<processor>>`; подтвержденный порт frontend-сервера — `5173`.
3. Frontend-приложение отправляет REST JSON-запросы на backend, размещенный на узле `Сервер приложения <<processor>>`; подтвержденный порт backend — `3001`, глобальный префикс — `/api`.
4. Backend NestJS API выполняется в Node.js runtime и обрабатывает запросы приложения.
5. Backend использует `Prisma Client <<library>>` как библиотеку доступа к данным.
6. Узел `Сервер приложения <<processor>>` соединяется с узлом `Сервер базы данных <<processor>>` по протоколу PostgreSQL.
7. PostgreSQL работает внутри Docker-контейнера `labyrinth-postgres`, запущенного Docker Engine на основании `docker-compose.yml`.
8. В локальной конфигурации проекта PostgreSQL проброшен как `5433:5432`; на диаграмме распределенной топологии нужно подписывать соединение как `PostgreSQL, порт 5432`, а локальный проброс `5433:5432` можно пояснить в тексте как особенность локальной конфигурации.
9. Данные PostgreSQL сохраняются в Docker volume `postgres_data`; на диаграмме это нужно назвать `Файлы данных PostgreSQL <<file>>`, а не `postgres_data <<file>>`.

  - компонент `Операционная система`;

  - компонент `Vite dev server`;
  - компонент `NestJS backend API`;
  - артефакт `Prisma Client <<library>>`;
  - артефакт `app/frontend <<source>>`;
  - артефакт `app/backend <<source>>`;
- узел `Сервер базы данных <<processor>>`;
  - компонент `Операционная система`;
  - компонент `Docker Engine`;
  - артефакт `docker-compose.yml <<file>>`;
  - компонент `Контейнер labyrinth-postgres`;
  - компонент `PostgreSQL 16`;
  - артефакт `Файлы данных PostgreSQL <<file>>`.

Предварительные физические соединения:

- `Клиент <<processor>>` — `Сеть <<net>>`: HTTP, frontend `5173`; HTTP / REST JSON, API `3001 /api`;
- `Сеть <<net>>` — `Сервер приложения <<processor>>`: HTTP, frontend `5173`; HTTP / REST JSON, API `3001 /api`; PostgreSQL protocol, порт `5432`;
- `Сеть <<net>>` — `Сервер базы данных <<processor>>`: PostgreSQL protocol, порт `5432`;
- при необходимости можно показать локальный проброс `5433:5432` не как межузловой адрес `localhost`, а как примечание к узлу базы данных.

Внутренние зависимости и размещение:

- `React frontend <<script>>` размещается на клиенте как код, выполняемый браузером;
- `app/frontend <<source>>` размещается на сервере приложения как исходники frontend, обслуживаемые `Vite dev server`;
- `app/backend <<source>>`, `NestJS backend API` и `Prisma Client <<library>>` размещаются на сервере приложения;
- `docker-compose.yml <<file>>`, `Docker Engine`, `Контейнер labyrinth-postgres`, `PostgreSQL 16` и `Файлы данных PostgreSQL <<file>>` размещаются на сервере базы данных.

Физические соединения между узлами нужно показывать UML-линиями без стрелок и подписывать протоколом/портом. Подписи на линиях через `Сеть <<net>>` должны читаться как маршруты трафика между физическими узлами. Зависимости между программными артефактами, если они будут показаны, должны быть пунктирными dependency-связями или заменяться вложением/текстовым описанием, чтобы не смешивать их с физическими соединениями.

## Risks and edge cases

- Главный риск — смешать методическую распределенную диаграмму в стиле эталона с буквальным локальным запуском через `localhost`. В утвержденном варианте диаграмма оформляется как логическая распределенная UML-топология, а локальные порты используются только как подтверждение технологий и конфигурации.
- Если оставить `localhost` на межузловых связях, это будет противоречить выбранному стилю эталона: `localhost` применим только внутри одной машины, а диаграмма показывает разные физические узлы.
- Если показать frontend как отдельный физический узел, это будет противоречить лекции, где узел является физическим вычислительным ресурсом. В утвержденном варианте frontend показывается как клиентский `<<script>>`-артефакт, выполняемый браузером.
- Если показать runtime-зависимости артефактов теми же линиями, что физические соединения между узлами, диаграмма будет смешивать нотацию диаграммы развертывания и диаграммы компонентов. Поэтому физические каналы и программные зависимости нужно разделять.
- Если показать Docker Compose как узел или среду выполнения, это будет методически спорно, потому что Docker Compose — инструмент/конфигурация запуска. Поэтому в утвержденном варианте `docker-compose.yml` является `<<file>>`.
- Если пометить установленные программы и сервисы как `<<executable>>`, диаграмма может выглядеть как смесь компонента и артефакта. Поэтому в утвержденном варианте программы и сервисы показываются как компоненты, а файловые стереотипы используются только для файлов, исходников, скриптов и библиотек.
- Если включить таблицы БД, классы, атрибуты или операции, диаграмма выйдет за область развертывания и начнет дублировать диаграмму классов или физическую модель данных.
- Номер рисунка `N` нельзя надежно зафиксировать без ручной синхронизации с `report/ours.docx`.
