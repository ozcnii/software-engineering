## Open questions

На момент утверждения плана приняты следующие решения:

1. Граница диаграммы — реализационная backend-модель: доменные сущности, Prisma-модели, DTO, controller/service classes. Это соответствует месту раздела `3.2.3` в блоке `Диаграммы реализации` и эталонному фрагменту про диаграмму классов на этапе реализации.
2. React-компоненты не включаются в диаграмму классов, потому что лекция описывает классы ООП, атрибуты, операции и связи, а React-компоненты проекта являются функциональными UI-компонентами и перегрузят UML-диаграмму классов.
3. Prisma-модели `User` и `Labyrinth` показываются как сущностные классы на основе `schema.prisma`, но без SQL/табличной детализации, чтобы не дублировать будущий раздел `3.3 Физическая модель данных`.
4. TypeScript union types показываются как UML-перечисления для читаемости диаграммы: `UserRole`, `LabyrinthTheme`, `GenerationAlgorithm`, `EntryMode`, `SolvingAlgorithm`, `MazeCell`. Значения перечислений показываются в API/backend-domain регистре из TypeScript-кода (`admin`, `player`, `winter`, `prim`, `auto`, `bfs`, `wall`), а не в Prisma-регистре (`ADMIN`, `WINTER`), потому что controller/service слой работает с DTO и domain values. Prisma-перечисления учитываются как источник типов для сущностей `User` и `Labyrinth`.
5. DTO-классы включаются только фактические backend DTO: `LoginDto`, `RegisterDto`, `GenerateLabyrinthDto`, `CreateLabyrinthDto`, `SolveLabyrinthDto`.
6. Для controller/service classes показываются только основные публичные операции, подтвержденные кодом; приватные helper-методы не показываются.
7. Используются профильные роли из лекции:
   - `AuthController`, `LabyrinthsController` — граничные классы;
   - `AuthService`, `UsersService`, `LabyrinthsService`, `GenerationService`, `SolvingService`, `RolesGuard` — управляющие классы;
   - `User`, `Labyrinth` — сущностные классы;
   - `Coordinate`, `MazeGrid`, `PublicUser`, DTO, response-структуры и перечисления — структурные классификаторы.
8. Для UML-нотации используются явные стереотипы:
   - `<<boundary>>` для controller classes;
   - `<<control>>` для service/guard classes;
   - `<<entity>>` для Prisma/domain entity classes;
   - `<<DTO>>` для request DTO classes;
   - `<<interface>>` для TypeScript interfaces и response-структур;
   - `<<type>>` для type aliases вроде `MazeGrid`;
   - `<<enumeration>>` для union/enumeration values.

Открытым остается только технический вопрос нумерации рисунка `N`, потому что итоговая нумерация зависит от ручного переноса в `report/ours.docx`.

## Data flow / API / state mapping

Будущая диаграмма классов должна отразить следующие связи:

1. `RegisterDto` наследует `LoginDto`.
2. `AuthController` использует `AuthService` и принимает `LoginDto`/`RegisterDto`.
3. `AuthService` использует `UsersService` и работает с `User`/`PublicUser`.
4. `RolesGuard` использует данные текущего пользователя и проверяет `UserRole`.
5. `LabyrinthsController` использует `LabyrinthsService` и принимает `GenerateLabyrinthDto`, `CreateLabyrinthDto`, `SolveLabyrinthDto`.
6. `LabyrinthsService` использует `GenerationService`, `SolvingService`, Prisma-модель `Labyrinth`, типы `MazeGrid`, `Coordinate`.
7. `GenerationService` использует `GenerateLabyrinthDto`, `GenerationAlgorithm`, `EntryMode`, `MazeGrid`.
8. `SolvingService` использует `SolvingAlgorithm`, `MazeGrid`, `Coordinate`.
9. `User` связан с `Labyrinth` отношением один-ко-многим: один пользователь может быть создателем многих лабиринтов.
10. `Labyrinth` содержит параметры ширины, высоты, темы, алгоритма генерации, режима входа/выхода и сетку лабиринта.
11. `LabyrinthDetailResponse` и `EntryExitPair` содержат `entry` и `exit` типа `Coordinate`; `Labyrinth` хранит `grid`, из которого эти координаты вычисляются при маппинге/валидации. На диаграмме нельзя показывать `entry`/`exit` как прямые поля Prisma-модели `Labyrinth`.
12. `MazeGrid` является двумерной коллекцией `MazeCell`.

## Risks and edge cases

- Главный риск — перегрузить диаграмму всеми backend и frontend файлами. Лекция допускает операции и связи, но эталон держит диаграмму и таблицу на уровне ключевых классов.
- Если построить только доменную модель, раздел может выглядеть слишком бедно для `3.2.3` как диаграммы классов на этапе реализации.
- Если включить React-компоненты, диаграмма может перестать быть UML-диаграммой классов в смысле лекции и стать перечнем UI-функций.
- Если Prisma-модели показать слишком подробно, раздел начнет дублировать физическую модель данных.
- TypeScript union types не являются классами в коде, поэтому в итоговой секции нужно явно пояснить их отображение как UML-перечислений.
- Номер рисунка `N` нельзя надежно зафиксировать без ручной синхронизации с `report/ours.docx`.

## Approval gate

Без отдельного подтверждения пользователя нельзя создавать или менять итоговый файл секции `report/sections/3.2.3-class-diagram.md` и файлы UML-диаграммы `diagrams/class/class-diagram.puml`, `diagrams/class/class-diagram.png`.
