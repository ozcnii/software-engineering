## Data flow / API / state mapping

Будущая компонентная диаграмма должна отразить следующие связи:

1. Пользователь работает с frontend-приложением React/Vite в браузере.
2. Frontend включает функциональные зоны аутентификации, администратора и игрока.
3. Frontend-зоны используют общий API-слой `shared/api`.
4. API-слой frontend взаимодействует с backend через REST JSON API: компонент `shared/api` отправляет запросы к компоненту `NestJS backend API`.
5. Backend NestJS API принимает REST JSON-запросы и передает обработку соответствующим backend-модулям.
6. `AuthModule` использует `UsersModule` для работы с пользователями.
7. `LabyrinthsModule` использует `GenerationModule` для генерации лабиринтов.
8. `LabyrinthsModule` использует `SolvingModule` для автоматического решения лабиринтов.
9. Backend обращается к PostgreSQL через Prisma Client.
10. Общие TypeScript-типы должны быть вынесены в `app/shared` и использоваться frontend и backend как единый контракт данных. На диаграмме они показаны отдельным компонентом `shared/types`; зависимости от него показываются только после того, как они подтверждены реальными импортами в коде.

В PlantUML связь между `shared/api` и `NestJS backend API` должна быть показана зависимостью с подписью `REST JSON`. Отдельный UML-интерфейс для этой связи не создается, чтобы не добавлять в диаграмму неподтвержденную проектом сущность.

## Risks and edge cases

- Если преподаватель ожидает строго файловый уровень компонентов, как в старом C#-эталоне, уровень NestJS/React-модулей может показаться более архитектурным. Этот риск снижается тем, что веб-проект фактически организован через frontend/backend-модули, а не через один исполняемый `.exe`.
- Если включить слишком много frontend React-компонентов, диаграмма начнет дублировать диаграмму классов или структурную схему. Поэтому на рисунке остаются зоны и API-слой, а конкретные UI-компоненты не перечисляются.
- Если раскрыть таблицы `User` и `Labyrinth` внутри компонентной диаграммы, раздел будет пересекаться с физической моделью данных. Поэтому в компонентной диаграмме показывается только PostgreSQL как компонент слоя данных.
- Если PlantUML недоступен в окружении, можно создать `.puml`, но PNG придется сгенерировать после установки или доступа к PlantUML. В текущей реализации нужно сначала проверить доступность PlantUML локально.
- Номер рисунка `N` нельзя надежно зафиксировать без ручной синхронизации с `report/ours.docx`.
- Если `app/shared` подключить только как type-only пакет без сборки JS, backend не должен импортировать из него runtime-значения. Если понадобятся общие runtime-константы, пакет `app/shared` должен иметь полноценную сборку в JavaScript перед сборкой backend.
- Если заменить backend DTO на интерфейсы из `app/shared`, сломается runtime-валидация `class-validator`. Поэтому общие типы используются как контракт, а DTO-классы остаются серверной реализацией проверки входных данных.
