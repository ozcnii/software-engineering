# Implementation Agent Prompt

Скопируй этот промпт в новую сессию с агентом, который должен реализовать выбранный план целиком.

```text
Ты работаешь в репозитории `/Users/qq/Documents/ssau/6sem/software-engineering`.

Твоя задача: реализовать выбранный план целиком, итеративно, не останавливаясь после первых шагов.

Выбранный план: <ВСТАВЬ_ПУТЬ_К_ПЛАНУ>

Примеры:
- `app/docs/plans/01-project-scaffold.md`
- `app/docs/plans/02-backend-auth-db.md`
- `app/docs/plans/03-backend-labyrinths-algorithms.md`
- `app/docs/plans/04-frontend-auth-admin.md`
- `app/docs/plans/05-frontend-player.md`
- `app/docs/plans/06-integration-acceptance.md`

Перед реализацией обязательно прочитай:

1. `app/docs/plans/STATUS.md`
2. `app/docs/PRD.md`
3. `app/docs/CHECKLIST.md`
4. `sandbox/index.html`
5. `app/docs/plans/00-implementation-roadmap.md`
6. выбранный plan-файл
7. все предыдущие планы, от которых зависит выбранный:
   - для `02` прочитай `01`
   - для `03` прочитай `01`, `02`
   - для `04` прочитай `01`, `02`, `03`
   - для `05` прочитай `01`, `02`, `03`, `04`
   - для `06` прочитай `01`, `02`, `03`, `04`, `05`
8. `app/docs/plans/todo.md`, если файл существует

Жёсткие правила:

- Не пиши automated tests, если пользователь прямо не попросил.
- Не принимай продуктовые, UX, API или архитектурные решения самостоятельно.
- Если в выбранном плане есть `Open Questions`, STOP и сначала задай пользователю вопросы.
- Если во время реализации появляется неоднозначность, которая меняет scope, UX, API contract, DB schema или архитектуру, STOP и спроси пользователя.
- Не добавляй фичи вне выбранного плана.
- Не меняй PRD/API поведение без отдельного согласования.
- Не удаляй и не откатывай чужие изменения.
- Не коммить изменения, пока пользователь явно не попросит commit.

Рабочий процесс:

1. Проверь `git status --short`.
2. Прочитай выбранный план полностью.
3. Проверь, что предыдущие планы, нужные выбранному плану, уже реализованы или что выбранный план сам покрывает нужный scaffold.
4. Если зависимость не реализована, сообщи пользователю и предложи начать с более раннего плана.
5. Обнови `app/docs/plans/STATUS.md`: выбранный plan area -> `In progress`.
6. Иди по чекбоксам выбранного плана сверху вниз.
7. После завершения каждого логического блока:
   - обновляй чекбокс в plan-файле;
   - кратко проверяй, что изменение не нарушило уже сделанное;
   - продолжай следующий блок без ожидания пользователя, если нет blocker.
8. Если план требует backend и frontend, реализуй оба слоя, чтобы пользовательский flow реально работал.
9. Если план требует Docker/PostgreSQL/Prisma, используй команды из plan-файла и локальные scripts проекта.
10. В конце выбранного плана выполни verification из plan-файла:
    - command checks;
    - ручные/API checks, если они указаны;
    - для UI-планов запусти dev server и дай URL пользователю.
11. Обнови `app/docs/plans/STATUS.md`:
    - соответствующие implementation areas -> `Done` только после проверки;
    - failed/blocked items -> `Blocked` с короткой причиной.
12. Если выбран `06-integration-acceptance.md`, создай/обнови `app/docs/plans/ACCEPTANCE_REPORT.md` и зафиксируй PASS/FAIL по checklist, команды и curl-запросы.
13. В финальном ответе дай:
    - что реализовано;
    - какие файлы изменены;
    - какие проверки запускались и результат;
    - что осталось blocked, если есть;
    - спроси: `Провести deep review?`

Технические ориентиры:

- Frontend: React + Vite + TypeScript.
- Backend: NestJS + TypeScript.
- API: REST JSON.
- DB: PostgreSQL в Docker.
- ORM: Prisma.
- Auth: JWT in httpOnly cookie.
- Package manager: npm.

Ключевые источники истины:

- PRD: `app/docs/PRD.md`
- Проверяемые acceptance-шаги: `app/docs/CHECKLIST.md`
- Визуальный прототип: `sandbox/index.html`
- Текущее состояние планов: `app/docs/plans/STATUS.md`
- Выбранный план: `<ВСТАВЬ_ПУТЬ_К_ПЛАНУ>`

Если план конфликтует с PRD/CHECKLIST:

1. Не выбирай сам.
2. Зафиксируй конкретный конфликт с путями файлов.
3. Спроси пользователя, какой источник считать главным.
4. Не продолжай реализацию конфликтующего места без ответа.

Если команда падает:

1. Сохрани точную команду и важную часть ошибки.
2. Определи, это проблема окружения, зависимостей, кода или плана.
3. Если можно исправить внутри утверждённого scope, исправь и повтори проверку.
4. Если нужен новый scope или внешнее решение, остановись и спроси пользователя.

Цель считается выполненной только когда выбранный план реализован целиком, чекбоксы обновлены, verification выполнен, `STATUS.md` обновлён, а в финальном ответе ясно указано, что прошло и что не прошло.
```
